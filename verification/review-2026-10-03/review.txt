Twinlight 项目评审与实验建议
评审日期：2026-10-03（Asia/Shanghai）

结论

项目已经具备可复用 skill 的基本结构：数据规范化、事实账本、叙事、确定性布局和网页渲染各有边界；引用采用消息 ID、文本哈希和字符范围；没有图像能力时保留明确占位；公开输出与私人原文分开。这些设计值得保留。

当前适合熟悉 Agent、Python 和 JSON 的使用者试用。直接面向普通用户时，安装、格式转换、批次编排和审查还需要较多宿主判断。大历史和反复增量更新存在已经复现的限制。现有测试能够证明许多程序约束成立，尚不能给出历史提取或分析的语义准确率。

本次没有修改业务实现、原有测试或 skill 指令。新增内容仅在 verification/review-2026-10-03/：复现实验、结果、浏览器验证材料和本报告。所有实验使用虚构数据；没有读取个人账户历史、调用外部模型或生成个人肖像。

实测范围

环境为 macOS、Python 3.12.14、Node 22.23.2、jsonschema 4.26.0、Pillow 12.3.0、Playwright 1.57.0。Python 依赖安装在 /private/tmp/twinlight-review-20261003-venv，示例页面位于 /private/tmp/twinlight-review-20261003-demo。临时目录不是长期安装位置。

1. 原有 unittest：66/66 通过。
2. 示例构建成功：3 主星、5 行星、明确占位图，HTML 为 4,232,723 字节。
3. 编译后的 JavaScript 通过 node --check。
4. 浏览器验证：23/23 通过，使用本机 Chrome 的 SwiftShader/ANGLE WebGL 路径。关 foil 的左右图像平均像素差为 10.637；关 depth 后为 0。没有页面异常或 HTTP/HTTPS 请求。
5. 容量用例：1 主星/0 行星、8 主星/64 行星通过手机尺寸布局检查。
6. skill-creator 基础校验通过。
7. 9 个针对性实验均复现了所记录的行为。它们包含实现问题和明确的语义能力边界，不能把这个数量当作 9 个独立代码缺陷。

未覆盖：真实用户提取准确率、不同模型重复运行、跨宿主完整执行、Safari、手机真机、持续性能、真实人物分层图质量。浏览器脚本的 environment 字段写死为 Linux，本次实际为 macOS；原始报告保留该字段，应按这里的实际环境理解。

需要优先解决的问题

P1：规范化丢失已知对话顺序。
位置：scripts/twinlight_core/history.py:64、148；make_chunks:177。
缺少时间戳的 Generic 消息按哈希 ID 重排；ChatGPT 已知 parent 链也没有保留下来。实验中原顺序 m1..m10 变成不同排列。相同时间戳也会按 ID 排列，而有日期和无日期的同一会话会被分开。后续 chunk 会沿这个顺序组织材料，增加指代、否定和更正被误读的风险。
建议：保留 conversation_sequence、parent_id 和 branch_id，按真实会话路径读上下文；时间戳只作为日期信息。没有日期不等于没有可知顺序。分块保留会话边界，并允许带相邻上下文；上下文片段与本块负责提取的片段应分开标记。

P1：合并在消歧之前被当前状态冲突卡住。
位置：scripts/twinlight_core/extraction.py:43–46；evidence.py:48–52。
两个 chunk 分别提取“我现在是设计师”“更正，我现在是教师”，具有相同 conflict_key、accepted/current 状态，merge-extractions 直接失败。人工增加 supersedes 后 verify 可以通过，说明数据能够正常消歧，但流程要求先完成合并再消歧。
建议：把来源/批次结构校验与最终语义状态校验拆开。合并阶段保留冲突候选并输出 conflict report，最终编译才拒绝未消解冲突。现有 complete=False 只放宽覆盖检查，不能解决这处问题。

P2：同一事实重复 9 次就超过证据上限。
位置：schemas/analysis.schema.json:162；extraction.py:31–32。
相同 fact ID 的证据会完整合并，但 schema 限制每个事实最多 8 条 evidence。9 条真实重复陈述、9 个 chunk 就能令合并失败，这与“保留重复事实的多份证据”不协调。事实总数另有 2000 上限，用户处置有 100000 上限；长历史应明确说明容量和停止行为。
建议：完整来源账本与展示用代表证据分开。可以限制展示 8 条，但不要静默截断真实来源。若暂时保留容量限制，应给出明确的归并策略与可恢复错误提示。

P2：引用与消息处置只做了单向绑定。
位置：scripts/twinlight_core/evidence.py:56–67。
给已存在事实追加一条来自“已排除消息”的准确引用，verify 仍通过；该消息的 disposition 仍说 third_party、fact_ids=[]。程序检查了 disposition -> evidence，没有检查每个 evidence -> disposition。
建议：对每条 (fact_id,message_id) 证据边，要求相应消息处置也列出该 fact_id。这样账本可以一致，语义上是否支持该事实仍需另行审查。

P2：审查稿遗漏了应当审查的内容。
位置：scripts/twinlight_core/compiler.py:89–108。
review.md 未列出排除消息及理由、未知日期和附件/分支缺口的详细统计；卡片只展示标题、tagline 和 reflection，没有完整关键词、英文标题和视觉符号。实验中的独有关键词和两条排除消息均没有进入审查稿。人工审查依赖这份文件时，很难发现错误排除和卡片过度解释。
建议：审查稿展示完整公开内容、对应 fact_ids、排除原文的必要上下文、理由、被替代事实关系、待确认项和覆盖缺口。敏感原文仍只保存在本地。

P2：增量布局没有复用已空出的轨道。
位置：scripts/twinlight_core/layout.py:46–58。
初始 8 行星，保留 1 个、替换另外 7 个，结果仍然只有 8 个，但新行星从旧布局的最外轨道继续追加，触发“Retained orbit slots exhausted”。旧位置得到保留，不过“插入空闲位置”的增量能力不足。
建议：在保留现有行星的情况下复用已删除对象留下的轨道空位。确实无法容纳时，输出具体受影响对象，再允许显式重排；不要只给笼统重置建议。

测试与视觉证据还有一个较小问题：scripts/verify_browser.py:26 只等 300ms，页面 app.js 的加载遮罩在 ready 后 1100ms 才隐藏。本次 home.png 主要仍是加载遮罩。状态检查通过不代表这个首页截图可以用于视觉验收。截图应等待 loading 真正隐藏、字体/图片完成和至少一帧稳定呈现。

历史提取和分析到底是否准确

程序能可靠检查：引用是否来自用户消息、是否精确、偏移与哈希是否对应；计划与问题的类型/状态组合；引用闭包；敏感、被替代或未接受事实不能进入公开引用；消息是否具有处置记录。原有测试在这些范围内有价值。

程序没有证明“原话支持结论”。实验保留“我计划学一点网页动画，还没有开始。”及其正确 plan 标签，只把主题 headline 改成“你已经掌握网页动画并完成作品。”，verify 与 compile 均通过。这是项目已声明的语义边界，不应宣传为语义真实性经过自动验证。

另一个实验把 10 条用户消息全部标记 not_personal，零事实，仍然得到 extraction_coverage_complete=true。空主题构建仍会被拒绝，但这个字段表示消息处置覆盖，不表示事实召回率。建议将它命名为 message_accounting_complete，并把语义评审状态独立记录。

用户自述有准确出处，也不等于现实经历经过外部查证。评测要区分：本人归属、原话支持、事件状态、叙事解释、外部真实性。不要把这些压成一个“准确率”。

扩展性与泛化性

扩展性：模块划分清楚，新增来源可以转换成通用历史结构，渲染器可以保持不变。当前 adapter 选择、格式参数和字段规则仍写在代码中，缺少适配器接口与迁移命令。增量更新主要依靠宿主维护 ID、旧账本和引用，没有自动 diff/update 工具。建议先补 SourceAdapter 的输入契约与兼容 fixtures，再补来源去重、版本差异和依赖变化的失效报告，无需马上做复杂插件平台。

泛化性：主题不固定为五章，区分问题/计划/成果，没有强制人格排名，适合不同人的成长材料。但现有示例几乎只有一位虚构用户的十条独立消息，没有充分测试真实长会话里的省略、否定、纠错、第三方引用及语言变化。CLI 只自动支持所列 JSON，不能直接接 ZIP、Markdown、截图或附件；英文副标题必填，UI/文案/卡风格主要是中文幻想成长叙事。若保持这个产品范围，可以把它明确说明；扩语言或扩任务类型应经过新数据集验证。

他人使用的便利性：README 的示例启动路径明确，离线 HTML 便于交付；但正常流程没有一个贯通的运行入口，依赖宿主生成正确 JSON、逐块产物、命令参数和图层。skill 命令多用相对路径，还依赖执行时的 cwd。建议增加环境 doctor、绝对 skill root、每次运行独立的工作目录、阶段状态和可恢复的 resume。普通使用者应主要提供导出文件、昵称和必要偏好，并审查结果；不应自己维护 hash、字符偏移和批次文件。

建议的测试与实验

A. 先补确定性回归。
将本次顺序、跨块纠错、9 条证据、双向处置和轨道替换用例转成以期望行为为断言的 tests。增加同时间戳、长消息跨块否定、emoji/组合字符、分支内更正、重复导出和相同原生 ID 内容编辑。保持现有 66 项程序检查。增加 Python 3.10/3.12/3.13、macOS/Windows/Linux 的有界矩阵，分别记录构建与可选浏览器能力。

B. 建立有标准答案的语义小基准。
第一轮可用 60–100 个虚构困难会话，加 12 位明确同意参与者、每人约 50 条有上下文的消息，作为约 600 条真实消息的小试验。按技术/非技术用户、不同语言、短/长会话、日期缺失、问题/计划/成果、第三方与角色扮演分层。长上下文和跨 chunk 情况单独构造，不能把 50 条短消息当作大历史验证。
两位标注者独立标注：原子事实、准确引用、本人归属、状态、明确更正、应排除内容及可发布范围，分歧再裁决。含糊项保留 uncertain，不强行制造标准答案。历史只进入参与者授权的存储和宿主。
分别报告：本人事实 precision、相关事实 recall、计划/成果混淆率、逐句叙事支持率、错误排除率、纠错保留率、敏感泄漏数。事实匹配按语义对照，不能仅比较 ID 或原文措辞。按用户和困难类型给出结果；较大样本时以用户为单位给出区间估计。
可把 precision 和叙事支持率 >=98%、recall >=85% 作为第一轮候选目标；他人经历错归本人、敏感泄漏和将明确“未完成”写成成果，在基准中应为 0。这些是建议门槛，不是已达到的成绩或真实环境零风险证明。

C. 比较模型与流程改动。
固定原文、schema、prompt 版本和运行配置，选择两个实际可用宿主模型，各重复三次；第一轮只跑文本，不生图。记录模型、工具权限、token、耗时、费用和修订次数。将用户分为调试集与最终留出集，避免用同一批数据反复调规则后又当作泛化成绩。
比较当前流程、保留会话上下文、拆开合并/消歧校验、增加独立语义复核四个版本。先在调试集单独改变一个因素，最后在留出集验证组合。第二次模型复核仍需用人工标准答案验证；不能因为模型同意就算正确。比较事实集合、状态和引用支持，不要求创作性主题措辞完全一致。

D. 测增量与规模。
增量分别加入新事实、明确更正、仅新增无关聊天、编辑旧消息和替换主题。检查旧语义 ID/坐标保留、新证据关联、被影响叙事失效、审批失效和差异说明。
用虚构数据在 1000/10000/50000 消息规模测 ingest/chunk/merge/verify 的耗时与峰值内存，另测真实宿主的 chunk 完成率、上下文消耗和重试恢复；本地脚本性能与模型提取成本分开报告。

E. 测首次上手和页面。
请 5 位未读实现的人，从已支持导出格式开始执行一次完整文本审查流程，记录完成率、主动求助次数、失败位置、首个可审查稿耗时和对“处理范围/占位图”的理解。宿主工具差异至少覆盖两种实际目标环境。
页面继续测试 1/8 主星和 0/64 行星，补真正加载完成后的截图、键盘焦点与错误态、实际 file:// 打开、Safari、手机真机及持续帧率。当前 23 项检查并没有证明以上所有情况。

复现本次评审

在项目根目录、Python 3.10+ 和项目依赖已安装的环境中执行：
  python -m unittest discover -s tests -v
  python verification/review-2026-10-03/experiments.py
  python scripts/twinlight.py demo --out outputs/review-demo
  node --check outputs/review-demo/compiled-check.js
  python scripts/verify_browser.py --html outputs/review-demo/index.html --out outputs/review-browser --require-webgl
  python scripts/check_capacity.py --out outputs/review-capacity.json

浏览器脚本支持 --browser；容量脚本支持 TWINLIGHT_BROWSER。按本地环境设置实际浏览器路径。上面的 experiments.py 会重新生成同目录 results.json；它是问题复现工具，成功运行不表示这些问题已修复。修复之后应把期望行为写入正式回归测试。

建议顺序：先修对话顺序和合并/消歧边界，再修来源容量、双向绑定、完整审查稿和增量轨道；随后完善首次运行流程，开展有标准答案的语义试验。视觉扩展可在这之后继续进行。
